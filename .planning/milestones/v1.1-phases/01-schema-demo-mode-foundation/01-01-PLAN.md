## Phase Goal

**As a** solo job-seeker building this tracker, **I want to** open a running app whose event-sourced schema, correction/override model, and demo/real data swap are proven end-to-end by one live page, **so that** every later feature is built on a persistence foundation I have seen actually work.

> This is a Walking Skeleton phase (WALKING_SKELETON=true). The "vertical slice" is the schema + migration + thin liveness path (proven in plans 01-01 and 01-02), not real feature UI — the pipeline board, job detail, and all real screens remain Phase 2 (see SKELETON.md). Note: the ROADMAP `**Goal:**` line for Phase 1 is stated system-facing ("the persistence foundation exists correctly"); this user story reframes it around the walking-skeleton capability per the planning-context walking-skeleton amendment.

<objective>
Scaffold the greenfield Next.js + TypeScript project on the `node:sqlite` driver (D-14), define the complete Drizzle schema for every Phase 1 table, generate and apply the first migration, and stand up the vitest test harness that every downstream plan depends on.

Purpose: This is the foundation of the walking skeleton. Everything else in Phase 1 imports the schema, the migrate runner, or the test helper created here. Getting the driver (node:sqlite, not better-sqlite3) and the append-only + projection + override + alias table shapes right now is un-retrofittable once data accumulates.
Output: A buildable project, one generated migration creating all 13 tables, a reusable in-memory test-DB helper, and a `.gitignore` protecting real data before any real data can exist.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| npm registry -> local install | Third-party package code enters the project at install time |
| developer/UI input -> Drizzle write path | Untrusted field values (esp. override field_name) cross into persistence |
| local repo -> public/portfolio git remote | Real job-search data or secrets could leak if committed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-SC | Tampering | npm installs (Task 2) | high | mitigate | RESEARCH Package Legitimacy Audit + consolidated blocking-human checkpoint (Task 1) before install; no `better-sqlite3`; no unlisted package |
| T-01-01 | Tampering | overrides.field_name | high | mitigate | Zod `overrideInput` constrains field_name to a fixed allow-list constant (Task 3); arbitrary column targeting rejected at the write boundary |
| T-01-02 | Information Disclosure | data/*.sqlite, .env in git | high | mitigate | `.gitignore` for `data/*.sqlite`, `data/*.sqlite-*`, `.env*` landed in Task 2 BEFORE any data directory exists (PITFALLS Pitfall 5) |
| T-01-03 | Tampering | raw SQL / string concatenation | medium | mitigate | Drizzle parameterized query builder used everywhere; any hand-written SQL uses `sql` tagged templates with bound params |
| T-01-04 | Spoofing/Tampering | credential-shaped columns | medium | accept | No credential/token column is added this phase (V6 N/A); Gmail token storage explicitly deferred to Phase 3 with its own design |
</threat_model>

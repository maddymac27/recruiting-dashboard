    - getMergedField returns the override value when an override exists, otherwise the derived value passed in.

    Create `src/domain/overrides.ts`. Export `setOverride(db, applicationId, fieldName, value)` that validates the input with `overrideInput` (rejecting any field_name outside the allow-list constant from validation.ts — V5), then runs a transaction that reads the existing `overrides` row for `(applicationId, fieldName)` and UPDATEs it (setting value_text and set_by_user_at) if present, else INSERTs a new row (RESEARCH Pattern 3; do NOT use `onConflictDoUpdate` on the composite key — Pitfall 2). Export `getMergedField(db, applicationId, fieldName, derivedValue)` returning the override's value_text if a row exists, else `derivedValue` (override always wins — DATA-07). The ingestion/derive path never reads overrides before writing; only the read path enforces precedence, so a re-sync structurally cannot touch an override.

    - "allow-list": setOverride with a field_name outside the allow-list throws/rejects.
    - "single row per field": setting the same field twice updates in place (one row), not two rows.

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|

| T-01-14 | Tampering | arbitrary override field_name | high | mitigate | `overrideInput` allow-list constant enforced at write boundary (V5) |
| T-01-15 | Tampering | unreliable composite-key upsert | medium | mitigate | explicit read-then-write transaction, never onConflictDoUpdate on (application_id, field_name) (Pitfall 2) |

<objective>
Land the two shared data-layer foundations every write slice (Wave 3) builds on: (1) the `[BLOCKING]` `postingUrl` schema migration that CAP-01's quick-save needs a column to write into, and (2) the `appendStatusEventTx` refactor that lets CAP-02's `updateApplication` and CAP-01's `quickSaveApplication` append a status event inside their own atomic transaction without hitting SQLite's no-nested-transaction limit. Also add the Zod schemas the write paths validate against.

## Phase Goal (user story, derived from ROADMAP Phase 2 goal + success criteria)

**As an** active job-seeker, **I want to** quick-save a job I'm considering (URL optional) and later edit any field or move its stage without ever corrupting the event-sourced history, **so that** my capture is fast and my record stays true — this plan is the schema + transaction groundwork that makes those writes safe.

Purpose: The schema-gate contribution and RESEARCH Pitfall 2 both require this land in Wave 1, before any write path or any test that reads `postingUrl`. Sequenced as an explicit dependency of the Wave 3 write slices.
Output: `postingUrl` column + migration, `appendStatusEventTx` helper, `quickSaveApplicationInput`/`updateApplicationInput` schemas, and extended tests.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| write-path input → SQLite | Untrusted (even single-user) input crosses into persistence; validated by Zod first |
| schema migration → live demo/real DB files | An ALTER must be additive and reversible-safe |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-03 | Tampering | postingUrl accepted by quickSaveApplicationInput/updateApplicationInput | high | mitigate | `z.string().url()` + http/https-only refinement rejects `javascript:`/malformed URIs at the write boundary before any persistence or later href render (ASVS V5). |
| T-02-04 | Denial of Service | migration corrupting existing rows | medium | mitigate | Migration is additive-only (nullable column, no default, no backfill); migrate.test.ts asserts existing table set intact + column nullable. |
| T-02-05 | Tampering | SQL injection via new write paths | low | accept | All writes use Drizzle's parameterized query builder; no raw string-interpolated SQL is introduced (matches project convention). |

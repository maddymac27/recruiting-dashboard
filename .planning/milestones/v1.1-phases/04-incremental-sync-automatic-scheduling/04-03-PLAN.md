<objective>
Make the sync run itself, unattended, and fail loud when it doesn't. Add `scripts/sync.ts` — the Windows Task Scheduler entrypoint that reuses the exact `runGmailSync` + sync-run lifecycle the manual action uses (D4-05, no fork), gated to real-mode, self-throttling the at-logon trigger via `getLatestSuccessfulSyncRun` (D4-02, 4-hour window). Add the checked-in `scripts/register-task.ps1` that registers the daily + at-logon triggers with `StartWhenAvailable` and NO `WakeToRun` (D4-01, catch-up-only). Add the D4-03 staleness alarm: a pure `isSyncStale` predicate, a `lastSuccessAt` prop computed in layout.tsx, and a prominent stale banner in ingestion-health surfaced ahead of the failed line.

Purpose: This is the ING-05 script/UI half and the fail-loud backstop that makes the catch-up-only model safe — if the machine was off for a week or the task silently stopped, the stale banner makes it impossible to miss on next open.
Output: A runnable `npx tsx scripts/sync.ts`, a one-time registration script, and a health UI that escalates on staleness.

MVP observable effect: a green throttle test + green staleness test; running the script in real mode records a sync_runs row; the health UI shows the stale banner past the 2-day threshold. (The OS trigger-firing half of ING-05 is verified in 04-04.)

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS Task Scheduler → node process | The scheduled action launches a process under the user's account; PATH/working-dir determine what runs |
| standalone script → .secrets/ token + Gmail (HTTPS) | Token read at rest outside the Next.js process; real vs demo store selected by mode |
| script logs → developer console | Unattended-run output could leak sensitive data if mislogged |

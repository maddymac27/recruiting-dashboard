## New Surfaces — Phase 3 Additions

Five new surfaces this phase, all rendered inside the existing Phase 2 nav-shell (`src/components/nav-shell.tsx`) — no new visual language, same shell chrome.

### 1. Sidebar — Ingestion Health block + Sync trigger + risk note

Lives in the left sidebar, below the DEMO badge slot and above the nav links (or immediately below nav links — planner's call on exact placement; must be visible on every page, not just Pipeline). Contains, stacked vertically at `sm` (8px) gaps:

- **Last-sync line**: "Last synced {relative time}" in Label-size text (14px/400, `text-muted-foreground`), or "Never synced" before the first run.
- **Sync now button**: accent-filled, full-width in the sidebar. States:
  - Idle: label "Sync now", enabled.
  - In-progress: disabled, label "Syncing…", `Loader2` icon spinning to the left of the label.
  - Success: returns to idle state; a `sonner` toast confirms ("Sync complete — {N} new, {M} to review"); last-sync line updates immediately.
  - Failure: returns to idle state but the last-sync line switches to destructive-colored text ("Last sync failed — {relative time}") and stays that way until the next successful sync (not just a transient toast — REL-03 requires an at-a-glance persistent signal, not something that disappears after 4 seconds). A `sonner` error toast also fires once per failed attempt.
  - Not-yet-connected (no OAuth token): button is disabled, wrapped in a `tooltip` reading "Connect Gmail to enable sync" (see Surface 5).
- **Review / Dead-letter count badges**: two small `Badge` + numeral pairs, e.g. "Review (12)" and "Dead-letter (2)", each linking to its respective queue route. Always show both numerals (even "0") so the sidebar communicates "at a glance" health per REL-03. Review-queue badge is always `variant="secondary"` (neutral — it's a queue of decisions, not failures). Dead-letter badge is `variant="secondary"` (muted) at 0, and switches to destructive-red styling the moment its count is > 0 — the only place in this phase where a numeral's color itself communicates "something failed."
- **Persistent risk note** (REL-04): a small, non-dismissible `alert` (no close button — it is not a transient toast, it must persist every time the shell renders), copy locked below. Neutral/muted styling (not destructive — this is a disclosed limitation, not a failure state), so it doesn't visually compete with an actual sync failure.

### 2. Review Queue (`/review` or equivalent route)

A table (shadcn `table`) of items awaiting a human decision, covering all three CONTEXT-defined item types: low-confidence match, unmatched "confirm & create," and label-mail (free-form). `Tabs` at the top filter **Pending / Resolved** (resolved items are never deleted — see Copywriting/Registry rationale below; they move to the Resolved tab as a permanent audit trail).

Columns: Type badge, Sender/Subject (truncated with ellipsis, full value on hover title-attribute), Parsed company/role if any (em-dash placeholder if absent — never literal "null"), Date, Actions.

Row actions by type (each opens the smallest dialog that gets the job done — reuse Phase 2 primitives, don't invent new ones):
- **Low-confidence match** → "Confirm match" (accent button, attaches to the suggested application) or "Choose different application" (opens a search/select, same dialog chrome as the Phase 2 add/edit dialog).
- **Unmatched / confirm & create** → "Create application" (opens the existing quick-save-style dialog, pre-filled from parsed company/role/date) or "Attach to existing" (search/select, same as above).
- **Label mail** → "Log as conversation" (opens the existing Phase 2 `contact-conversation-form.tsx`, pre-filled with the email's date and verbatim text as the conversation note; user picks the target application).

No "skip" action needed as a distinct control — not acting on a row simply leaves it in Pending; the user works through the table at their own pace. This matters given D3-06's large one-time backfill.

**Pagination**: given the historical-backfill volume, the table paginates at **25 rows/page** with a "Load more" button at the bottom rather than numbered pages or unbounded infinite scroll — simplest control that stays usable at high counts without added scroll-position complexity.

### 3. Dead-letter Queue (`/dead-letter` or equivalent route)

Same table/tabs/pagination pattern as the Review Queue (Pending/Resolved tabs, 25/page, "Load more"). Two item types per D3-04: **unparseable mail** (unknown sender or a known sender template Wasn't recognized at all) and **known-sender parse failure**, both flagged and never silently dropped.

Columns: Type badge (destructive-red for "known sender failed to parse" — this is the flag D3-04 requires; neutral/secondary for generic unparseable), Sender/Subject, Date, "View raw email" action.

**"View raw email" opens a Dialog containing a `scroll-area`.** Security-relevant rendering rule (this content is externally-sourced and untrusted by definition): the raw email body renders as **escaped plain text only** (e.g. a `<pre>`/text node, never `dangerouslySetInnerHTML`), regardless of whether the source was HTML or plain-text MIME — matches the project's existing "free text rendered escaped" convention (see 02-UI-SPEC/CONTEXT code-context notes) and specifically protects against a malicious or malformed email body being interpreted as markup inside the dashboard. No truncation of the raw content itself (full fidelity matters for diagnosing why the parser failed); only the table's Subject column truncates.

Items move to "Resolved" only when a later sync/re-parse of the **same message id** succeeds (domain-layer concern, not a manual dismiss button in the UI — there is no user-facing "delete" or "ignore" control for dead-letter items in v1, consistent with REL-02's never-silently-discard intent and Phase 2's precedent of never exposing a destructive/delete action).

### 4. Manual Sync Trigger

Covered as part of Surface 1 (sidebar). No separate page. `Loader2` spin animation is the only "loading" affordance needed — no progress bar/percentage (sync duration and item count aren't predictable enough to show meaningful progress).

### 5. OAuth Connect Affordance (one-time)

Minimal, since CONTEXT confirms this is a one-time developer action, not a recurring user flow. Before any token exists, the sidebar's Ingestion Health block (Surface 1) shows a **"Not connected"** state in place of the last-sync line, with a **"Connect Gmail"** button (accent-filled, same visual weight as "Sync now" would be) that redirects to Google's OAuth consent screen and returns via the server-side callback route. Once a token is successfully stored, this state never reappears for that install — it is permanently replaced by the normal idle/in-progress/success/failure sync states. No dedicated settings page is needed this phase.

## Color

Reused base tokens verbatim from `02-UI-SPEC.md`. This phase is the **first to actually use the Destructive token** (Phase 2 declared it reserved/unused) and extends the Accent reserved-for list.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FFFFFF` | Page background, dialog surfaces, queue table background |
| Secondary (30%) | `#F4F4F5` (zinc-100) | Cards, sidebar/nav background, queue table row stripes, neutral badges (review-queue type badges, dead-letter count at 0) |
| Accent (10%) | `#2563EB` (blue-600) | "Sync now" button, "Connect Gmail" button, "Confirm match" / "Create application" / "Log as conversation" primary actions inside review-queue dialogs, active nav link (unchanged from Phase 2), tab active-indicator (Pending/Resolved), focus rings |
| Destructive | `#DC2626` (red-600) | **First use this phase**: "known sender failed to parse" type badge (dead-letter), the dead-letter count badge once its count is > 0, the sidebar's "Last sync failed" text state |

Accent reserved for: the elements listed above — never applied to body text, table row backgrounds, or non-primary buttons (e.g. "Choose different application" / "Attach to existing" stay neutral/outline-styled, not accent-filled, since "Confirm"/"Create"/"Log" are each screen's one primary action).

Destructive reserved for: failure signals only (known-sender parse failure, sync failure, dead-letter count > 0) — **never** applied to the review-queue's uncertain-but-not-failed items (low-confidence match, unmatched, label mail all stay neutral/secondary badges, since uncertainty needing a decision is not the same signal as something broken). No new semantic color (e.g. amber/warning) is introduced — the REL-04 risk note deliberately uses neutral/muted styling, not destructive, since it is a disclosed limitation, not an active failure.
